# Real‑Time Retrieval‑Augmented Generation over Model Context Protocol (RT‑RAG‑MCP)

**Abstract** – Large language models excel at generating fluent text, yet their knowledge is frozen at training time. Retrieval‑augmented generation (RAG) remedies this by letting the model query an external knowledge base during inference. Existing RAG pipelines are largely *batch* systems: a single query is issued, documents are fetched, and the LLM produces a final answer in one request–response cycle. This paper introduces **Real‑Time Retrieval‑Augmented Generation over Model Context Protocol (RT‑RAG‑MCP)** – an event‑driven framework that decouples retrieval from generation while preserving a persistent internal context. RT‑RAG‑MCP extends the OpenAI “Chat Completions” API with *retrieval directives* and *context tokens*. The model can interleave multiple rounds of search and synthesis, allowing it to refine its answer in real time. We formalise the protocol, describe an implementation built on HuggingFace Transformers (Falcon‑40B) + FAISS for vector search, and evaluate on Natural Questions, TriviaQA, and a curated scientific‑literature benchmark. Results show a 27 % reduction in hallucination rates, a 15 % boost in BLEU‑4 scores relative to conventional RAG, while keeping average latency under 350 ms per turn. Deployment considerations (caching, rate‑limiting, privacy) and avenues for future work (adaptive retrieval policies, multimodal extensions) are discussed.

---

## 1 Introduction

Large language models (LLMs) have demonstrated remarkable abilities in natural language understanding and generation, yet their knowledge remains static: once trained on a corpus, the parameters encode facts that are only as recent as the training data. Retrieval‑augmented generation (RAG) addresses this by allowing the model to query an external knowledge base at inference time, thus grounding its output in up‑to‑date evidence.

Current RAG systems, however, typically operate in a *single shot*: the user’s prompt is sent to the LLM; the LLM emits a retrieval directive (e.g., “retrieve top‑5 passages about X”); the system performs the search, returns the documents; finally the model generates the answer using the retrieved context. This one‑pass paradigm has several shortcomings:

1. **Hallucination** – The model may still hallucinate facts that are not supported by any retrieved document because it has no mechanism to verify or refine its earlier output.
2. **Coherence loss** – When multiple documents are needed, the LLM must synthesize them in one go, often producing fragmented responses.
3. **Latency overhead** – Each retrieval adds network I/O and CPU time; batching multiple retrievals can inflate latency beyond acceptable limits for conversational systems.

We propose a protocol that allows the model to *interleave* retrieval and generation within a single turn. The LLM can ask for more evidence, incorporate it into its internal context, refine its answer, and finally stop when satisfied. This is analogous to how humans conduct research: they read a passage, question it, search again, and iterate until confidence is achieved.

## 3 Problem Statement

Let \( q \) be an input query from a user. The goal is to produce an answer \( a \) that satisfies:

1. **Factual correctness** – Every factual claim in \( a \) must be supported by at least one retrieved document.
2. **Coherence** – \( a \) should read as a single, well‑structured response.
3. **Latency constraint** – The entire process (retrieval + generation) must complete within \( L_{\max} = 350\; \text{ms} \) on commodity GPUs.

Formally, we define the *Real‑Time Retrieval‑Augmented Generation* problem as:

> Find a sequence of retrieval–generation steps \( \{(R_t, G_t)\}_{t=1}^{T} \) such that
> \[
> a = G_T(\bigcup_{i=1}^{T-1} R_i, C_0),
> \]
> where \( C_0 \) is the initial context (the user’s prompt), each \( R_t \) returns documents \( d_t \), and the total latency
> \[
> \sum_{t=1}^{T} \bigl( \text{latency}(R_t) + \text{latency}(G_t) \bigr) \leq L_{\max}.
> \]

The challenge is to design a protocol that lets the model decide when and how many retrievals to perform, while keeping latency within bounds.

## 4 System Architecture

### 4.1 Model Context Protocol (MCP) Overview

We extend the standard *Chat Completions* payload with three new fields:

| Field | Description |
|-------|-------------|
| `context_id` | UUID that ties all messages in a conversational turn. |
| `state_hash` | SHA‑256 hash of the current internal context; used for cache validation. |
| `retrieval_directive` | Optional JSON object specifying retrieval parameters (top_k, filters). |

The model’s response may include a special token `<<RETRIEVE>>` that triggers the retrieval layer.

### 4.2 Real‑Time Retrieval Layer

- **Index:** FAISS IVF‑PQ index built over embeddings of all passages in the knowledge base.
- **Hybrid search:** Dense vector search followed by BM25 keyword filtering to reduce noise.
- **Retrieval API:** Exposes an HTTP endpoint `/retrieve` that accepts a query string and returns the top‑k documents along with relevance scores.

### 4.3 Interaction Flow

1. **User → Server**: Sends message `m_0 = {role:"user", content:q}`.  
2. **Server**: Generates a `context_id`, stores empty context `C_0`.  
3. **Model (Falcon‑40B)**: Emits partial response containing `<<RETRIEVE>>` and a directive.  
4. **Server → Retrieval Layer**: Executes query, returns documents \( d_1 \).  
5. **Server**: Updates internal context `C_1 = C_0 ∪ d_1`.  
6. **Model**: Continues generation conditioned on `C_1`, may emit another `<<RETRIEVE>>` if needed.  
7. **Repeat** until the model outputs a stop token or reaches maximum steps \( T_{\max} \).  

The protocol is *event‑driven*: each retrieval is triggered by the model, not pre‑planned.

---

## 5 Formal Specification of RT‑RAG‑MCP

Let:

- \( M \) be the language model,
- \( R \) be the retrieval function,
- \( C_t \) be the context after step \( t \),
- \( S_t \) be the partial output after step \( t \).

The protocol can be described by the following recurrence:

\[
\begin{aligned}
C_0 &= m_0,\\
S_{t+1} &=
M(S_t, C_t; \theta_M),\\
\text{if } S_{t+1}\!\!\downarrow_{\text{RETRIEVE}} &\Rightarrow
\begin{cases}
d_{t+1} = R(q_{t+1}; \theta_R)\\
C_{t+1} = C_t \cup d_{t+1}\\
S_{t+2} = M(S_{t+1}, C_{t+1}; \theta_M)
\end{cases}
\end{aligned}
\]

where \( q_{t+1} \) is the query extracted from `RETRIEVE` directive, and \( \downarrow_{\text{RETRIEVE}} \) denotes that the output contains a retrieval trigger. The process terminates when the model emits `<<STOP>>` or reaches \( T_{\max} \).

**JSON Schema (excerpt)**

```json
{
  "messages": [
    {"role":"user","content":"What is the latest research on graphene superconductivity?"},
    {"role":"assistant","content":"<<RETRIEVE>> top_k=3 source=\"arxiv\""}
  ],
  "context_id":"123e4567-e89b-12d3-a456-426614174000",
  "state_hash":"a1b2c3d4..."
}
```

## 6 Implementation Details

### 6.1 Hardware & Software Stack

| Component | Version |
|-----------|---------|
| GPU | NVIDIA A100 (40 GB) – inference only |
| CPU | Intel Xeon Gold 6248R, 2×24 cores |
| SSD | NVMe PCIe 4.0, 2 TB |
| OS | Ubuntu 22.04 LTS |
| Frameworks | PyTorch 2.0, HuggingFace Transformers 4.44, FAISS‑GPU 1.7.3 |
| Language Model | Falcon‑40B (checkpoint from EleutherAI) |
| Retrieval Engine | FAISS (IVF_PQ with 8192 lists), BM25 via ElasticSearch v8.10 |
| API Layer | FastAPI v0.109, Uvicorn |

### 6.2 Index Construction & Maintenance

1. **Corpus**: Wikipedia dumps + arXiv PDFs (≈ 50 M passages).  
2. **Pre‑processing**:
   - Tokenization with SentencePiece.
   - Chunking: 512 tokens per passage, overlap 64 tokens.
3. **Embedding**: All‑MiniLM-L6-v2 (384‑dim) via `sentence-transformers`.  
4. **FAISS Index**:
   - IVF_PQ: 8192 inverted lists, PQ dimension 128, code size 8 bytes.
   - Pre‑computed norms for efficient L2 search.
5. **Reindexing policy**: nightly incremental updates; new documents added to a *staging index* and merged with the main index via `faiss.IndexIVFPQ.merge()`.

### 6.3 API Design

| Endpoint | Method | Payload | Response |
|----------|--------|---------|----------|
| `/chat` | POST | JSON (messages, context_id) | JSON (assistant messages + finish_reason) |
| `/retrieve` | POST | `{ "query": "...", "top_k": 5, "filter": {"source":"arxiv"} }` | JSON array of documents with `id`, `title`, `snippet`, `score` |

**Latency Budget**:  
- Retrieval: < 80 ms (FAISS query + top‑k extraction).  
- Generation step: < 200 ms (Falcon inference on 1 GPU).

The FastAPI server orchestrates the loop, ensuring that each retrieval–generation pair stays within budget.

### 7.1 Datasets & Metrics

| Dataset | Size | Annotation |

| TriviaQA | 95 k QA pairs | Fact‑checked |

**Metrics**

- **Exact Match (EM)** and **F1** for NQ.
- **BLEU‑4**, **ROUGE‑L** for TriviaQA.
- **Hallucination Rate**: % of sentences containing unsupported facts (human annotation).
- **Latency**: average inference time per turn.

### 7.2 Baselines

1. **ChatGPT‑style** – Falcon‑40B without retrieval (pure generation).  
2. **Baseline RAG** – Single retrieval step before final generation.  
3. **RT‑RAG‑MCP** – Proposed protocol with iterative retrieval.

All models were fine‑tuned on the same training set using LoRA adapters (rank 8) to reduce inference memory footprint.

## 8 Results & Discussion

| Model | EM | F1 | BLEU‑4 | Hallucination % | Avg Latency (ms) |
|-------|----|----|--------|-----------------|------------------|
| ChatGPT‑style | 12 % | 21 % | 28 | 45 | 310 |
| Baseline RAG | 27 % | 36 % | 35 | 32 | 340 |
| **RT‑RAG‑MCP** | **34 %** | **44 %** | **42** | **20** | **350** |

### Observations

1. **Hallucination Reduction**: RT‑RAG‑MCP’s iterative retrieval allows the model to verify earlier claims before finalizing them, cutting hallucinations by 27 %.  
2. **Answer Quality**: BLEU‑4 improvement of 15 % over baseline RAG indicates more coherent synthesis.  
3. **Latency**: Despite additional round‑trips, the protocol stays within 350 ms thanks to efficient indexing and batched inference.

### Ablation Studies

| Variant | EM | Hallucination % |
|---------|----|-----------------|
| No context persistence (reset after each retrieval) | 28 % | 35 % |
| Fixed `top_k=1` | 31 % | 25 % |
| Retrieval only on *confidence* < 0.7 | 32 % | 22 % |

These results confirm the importance of context persistence and adaptive retrieval depth.

## 9 Deployment Considerations

### 9.1 Rate‑Limiting & Fairness
- **Token bucket** per user: 5 queries/min.  
- Prioritise *high‑confidence* requests for real‑time services; defer low‑priority ones to batch jobs.

### 9.2 Privacy & GDPR
- Knowledge base is hosted on a private cluster; no external API calls.  
- All retrieval logs are anonymised and stored encrypted; user data deleted after session expiry.

### 9.3 Caching Strategy
- **LRU cache** for the last 10 k retrieval results per `context_id`.  
- Cache invalidated when underlying index is updated.

### 9.4 Scalability
- Shard FAISS across GPUs (32‑GPU cluster) using `faiss.IndexShards`.  
- Deploy API behind a Kubernetes ingress with autoscaling based on CPU utilisation.

## 10 Future Work

1. **Adaptive Retrieval Policy**: Train a policy network to decide *when* to retrieve and *how many* documents, optimising a joint reward (accuracy + latency).  
2. **Multimodal Retrieval**: Incorporate image embeddings for visual knowledge bases; extend the protocol to handle multimodal context.  
3. **Explainability Layer**: Generate provenance chains automatically linking each factual claim to its source passage.  
4. **Continual Learning**: Periodically fine‑tune the model on newly retrieved documents without catastrophic forgetting.

---

## 11 Conclusion

RT‑RAG‑MCP demonstrates that a lightweight, event‑driven protocol can bring real‑time retrieval into conversational LLMs while preserving factuality and coherence under stringent latency constraints. By allowing the model to interleave search and synthesis, we reduce hallucinations dramatically and improve overall answer quality. The framework is modular, easily extensible, and ready for deployment in production systems that demand both speed and reliability.
